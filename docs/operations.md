# 運用ガイド（SaaSとして公開するまで・公開してから）

製品名「Kintai」は仮名です。正式名は `src/brand.ts` の1か所を書き換えます（画面・メール・公開サイト・規約がすべて追従します）。

## 1. 構成

```
ブラウザ ─HTTPS→ Caddy ─→ アプリ（Node.js 1プロセス）
                           ├─ /            公開サイト（LP・規約）… ビルド済みの静的HTML
                           ├─ /app/        管理画面・打刻画面（React）
                           └─ /api/        API
                                 ├─ control.db        会社の一覧・契約状態（Stripe の顧客ID 等）
                                 └─ tenants/<ID>.db   会社ごとのデータ（会社1社＝ファイル1つ）
```

- **会社ごとにDBファイルを分ける**構成です。他社のデータを読み書きする経路がなく、バックアップ・書き出し・削除が会社単位でできます。
- **単一サーバー前提**です（SQLite）。数百社・数千人規模までは1台で足りる想定ですが、冗長化（複数台）はできません。規模が出てきたら PostgreSQL への移行を検討してください（データ層は `src/server/repo.ts` と各ルートに集中しています）。

## 3. 起動

```bash
cp .env.example .env   # 値を埋める
docker compose up -d --build
curl https://<ドメイン>/api/health      # {"ok":true}
```

- 公開サイトは `https://<ドメイン>/`、アプリは `/app/` です。
- データは Docker のボリューム `app-data`（コンテナ内 `/data`）にあります。**ボリュームを消すとデータが消えます**。
- 更新: `git pull && docker compose up -d --build`。DB のスキーマ変更（マイグレーション）は、各社のDBを開くときに自動で適用されます。更新の前に必ずバックアップを取ってください。

> この Dockerfile / compose は、手元の環境では Docker を使えなかったため、**イメージのビルドは未検証**です（アプリ本体のビルドと、`node dist-server/index.js` での起動は確認済み）。初回は、ステージングでビルドと起動を確認してください。

## 4. Stripe の設定

**先にテストモードで全部通してから、本番キーに切り替えます。**

1. **商品と料金**を作る: 商品名（例: 勤怠管理）、**通貨 JPY、月次の定期課金、単価300円、数量課金（licensed / 数量はお客様の人数）**。料金の ID（`price_...`）を `STRIPE_PRICE_ID` に設定
2. **Webhook** を追加: URL `https://<ドメイン>/api/billing/webhook`。送信するイベントは次の6つだけにする
   - `checkout.session.completed`
   - `customer.subscription.created` / `customer.subscription.updated` / `customer.subscription.deleted`
   - `invoice.paid` / `invoice.payment_failed`

   表示される署名シークレット（`whsec_...`）を `STRIPE_WEBHOOK_SECRET` に設定
3. **カスタマーポータル**を有効にする（設定 → Billing → カスタマーポータル）: 「支払い方法の更新」「請求書履歴」「サブスクリプションのキャンセル」を許可。**ここを保存しないと「請求・お支払い方法の管理」が開けません**
4. **消費税**: Stripe Tax を使う場合は有効化し、`STRIPE_AUTOMATIC_TAX=1`。使わない場合は、料金を税込で設定するか、税率を料金に設定する
5. シークレットキー（`sk_live_...`）を `STRIPE_SECRET_KEY` に設定し、アプリを再起動
6. ローカルでの確認: `stripe listen --forward-to localhost:8787/api/billing/webhook` で表示される `whsec_` を使う

**動作の要点**
- 申し込みは Checkout、人数が増減したら数量を自動で更新（日割り）。更新に失敗しても社員の登録は止まらず、1時間ごとのジョブが再同期します
- 支払いに失敗すると `past_due`。**14日の猶予**のあと閲覧のみになります
- Webhook は署名を検証し、同じイベントの再配信・古いイベントの逆戻りは無視します
- ⚠️ **この実装は、Stripe 本体との実接続を一度も行っていません**（テストは、Stripe SDK の署名機能とダミーのゲートウェイで行いました）。テストモードで、申し込み → 人数変更 → 支払い失敗 → 解約 を必ず通してください。API の仕様変更に備え、`stripe` のバージョンは固定して更新時に確認します

## 5. バックアップと復元

```bash
docker compose exec app node --disable-warning=ExperimentalWarning dist-server/cli.js backup /data/backups --keep 14
# または deploy/backup.sh を cron で（毎日）
```

- SQLite の `VACUUM INTO` で、稼働中でも一貫したスナップショットを `backups/YYYYMMDD-HHMMSS/` に作ります（`control.db` と、会社ごとの `<ID>.db`）
- **同じサーバーのディスクにあるだけでは、サーバーの故障で一緒に失われます。** 別の場所への複製（`deploy/backup.sh` の末尾の例）を必ず設定してください
- **復元**: アプリを止め、`control.db` を `/data/control.db` に、`<ID>.db` を `/data/tenants/` に戻して、アプリを起動します。1社だけ戻す場合は、その会社の `<ID>.db` だけを置き換えます（`-wal` `-shm` ファイルは削除する）
- 復元の手順は、**公開前に一度、別環境で実際に試してください**

## 6. 解約・削除・データ提供

- 解約すると、会社は**閲覧のみ**になります（管理者は「会社設定」から全データをJSONで書き出せます）
- 規約では、契約終了から30日で削除する定めです（`src/brand.ts` の `policy.retentionDays`）。削除は手動です:
  ```bash
  ops list                                   # 会社の一覧（企業ID・状態・人数）
  ops export <企業ID> /data/export.json       # 念のため書き出し
  ops backup                                 # 念のためバックアップ
  ops delete <企業ID> --yes                  # 完全に削除（元に戻せません）
  ```
  （`ops` は `docker compose exec app node --disable-warning=ExperimentalWarning dist-server/cli.js` の略）
- バックアップには削除済みの会社のデータが残るため、**バックアップの保持期間（既定14世代）も、プライバシーポリシーの保存期間に反映してください**
- 利用の停止（未払いなど）: `ops set-status <企業ID> suspended`。ログインできなくなります

## 7. 監視

- `GET /api/health` を外形監視（UptimeRobot 等）に登録する
- ログは標準出力（`docker compose logs -f app`）。Stripe 関連のエラー（座席数の反映失敗など）は `座席数の反映に失敗しました` として出ます
- ディスク容量（`/data` と、バックアップの置き場）

## 8. セキュリティの現状と、未対応のこと

実装済み:
- パスワード: scrypt（非同期。リクエスト処理を止めない）。パスワード変更は成功も回数を数えて制限
- ログイン: 社員ID×IP単位（5回失敗で5分）・アカウント単位（20回失敗で15分）・IP単位の制限。他人が失敗を重ねて管理者を締め出しにくい設計
- 本文サイズの上限（通常64KB／Stripe通知1MB／CSV取り込み3MB。Caddy側にも3MB）
- 会社ごとのDB分離、Cookie（HttpOnly・SameSite・本番はSecure）、CSRF対策（別オリジン拒否）、CSPなどのヘッダー
- パスワード再設定（1回限り・60分・Hostヘッダ非依存）、一時パスワードの強制変更、最後の管理者の保護、操作記録（監査ログ）
- Stripe: 署名検証、重複配信・古いイベントの無視、**運営者が停止した会社はStripeの通知で自動復活しない**
- **登録時のメールアドレス確認**: 登録メールのリンク（24時間・1回限り・ハッシュで保存、再送すると古いリンクは無効、アドレス変更後は変更前宛のリンクも無効）。未確認の間は、**お申し込み（決済）・トライアル終了の案内メール・パスワード再設定メールが使えない**（他人のアドレスで登録されても、そのアドレスへ繰り返し送られない）。トライアル自体は未確認でも使える。入力ミスは、ログイン後の画面上部から直して再送できる（1時間に5回まで）。APP_URL 未設定でメールを送れない環境では、確認済みとして登録される。この機能の導入前に登録済みの会社は、確認済みとして引き継ぐ
- 案内メールに入る「会社名・お名前」は、改行・URLを受け付けない
- CSV出力は、数式として実行されうる文字列（`= + - @` で始まる）を無害化
- 本番でSMTP未設定のとき、メール本文（再設定リンク）をログに出さない

**この節の確認について**: 実装とは別の観点で、サーバーのコードを1度レビューし、指摘（本文サイズ無制限・同期的なパスワード計算・停止中の会社の自動復活など）を修正しました。ただし、これは**専門家による脆弱性診断の代わりにはなりません**。公開前に、第三者による診断（侵入テスト）を受けることを推奨します。

**未対応**（必要に応じて計画に入れる）:
- 登録時の確認メールそのものは、他人のアドレスにも1通届きます（IPごとに1時間10回まで。会社名・お名前にはURLと改行を入れられない）。メール爆弾を完全には防げないため、送信元ドメインの SPF・DKIM・DMARC と、必要なら CAPTCHA の導入を検討してください
- 二要素認証（管理者向け）、SSO
- ログイン失敗などの試行回数がメモリ保持（再起動で消える）。複数台構成では共有されない
- パスワードの計算はNodeのスレッドプール（既定4本）で行うため、大量の同時ログイン試行があると、他のログインが遅くなります（IP単位の制限で緩和）
- 監査ログの閲覧画面（今はデータベースと書き出しJSONにのみ記録）
- 会社の管理者がいなくなった場合の復旧手順（現状は運用者が `ops` とDB操作で対応）

### 簡略化していること（実運用で合わない場合は個別に確認が必要）

- 変形期間の途中から始まる週・途中で終わる週（月をまたぐ週など）は、週の判定をせず、期間の総枠で判定します。
- 時間外は「発生した日」（累計がしきい値を超えた日）に割り当てます。月をまたぐ週の週超過は、超えた日の月に入ります。
- **1年単位の変形の要件（労働日数の上限280日、1日10時間・週52時間の上限、連続労働日数、対象期間の労使協定の届出）は、チェックしていません。**シフトの作成・届出は運用側で確認してください。
- 1年単位の変形期間の途中で入社・退職した社員の賃金精算（途中退職時の清算）は扱いません。
- フレックスタイム制の「清算期間中の不足時間の繰越」「コアタイム・フレキシブルタイムの違反判定」は、注記・表示のみで、集計には影響しません。
- 交替制（8時間3交替など）で、番方による休日（継続24時間）を休日とする特例は扱いません。休日は暦日で判定します。
- 週の法定労働時間が44時間（特例措置対象事業場）の設定は、日の8時間を変えず、週・総枠の判定だけに使います。
- 変形・フレックスの社員の「本日の集計」（打刻画面）は、日8時間のしきい値による目安です。
- 月末見込は、これまでの実績が所定の何倍だったかのペースを、残りの予定に当てはめた推計です。
- 位置情報の判定は、ブラウザから送られた値を使うため、端末側で書き換えられる可能性があります（不正の完全な防止ではなく、確認の目安です）。

### 打刻手段の運用メモ

- **共用の打刻端末**: 会社設定で端末を登録し、表示されるURLを端末のブラウザで開く（トークンは端末に保存され、URLからは消えます。失くした場合は端末を無効にして登録し直す）。社員は ICカード（キーボードとして動作する USB カードリーダーが、カード番号＋Enter を入力する方式）か、社員ID＋6桁の暗証番号で確認する。確認は90秒・1回限り。暗証番号は、同じ社員に5回続けて失敗すると5分ロックされる。**カードリーダー実機での動作は検証していません**（キー入力の再現でのみ確認）。
- **位置情報**: 会社設定で「記録する」「範囲外では打刻できない」を選べる。位置情報は個人情報なので、社員への周知とプライバシーポリシーへの記載が必要（ひな形に追記済み・要確認）。無効のときは、送られてきても保存しない。
- **給与用CSV**: 勤怠一覧の「給与用CSV」から、社員ごとの月次集計・日別明細を出力（UTF-8・BOMつき）。給与ソフトごとの取り込み形式には合わせていません。

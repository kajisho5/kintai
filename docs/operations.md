# 運用ガイド（SaaSとして公開するまで・公開してから）

製品名「Kintai」は仮名です。正式名は `src/brand.ts` の1か所を書き換えます（画面・メール・公開サイト・規約がすべて追従します）。

## 1. 構成

```
ブラウザ ─HTTPS→ Caddy ─→ アプリ（Node.js 1プロセス）
                           ├─ /            公開サイト（LP・規約）… ビルド済みの静的HTML
                           ├─ /app/        管理画面・打刻画面（React）
                           └─ /api/        API
                                 ├─ control.db        会社の一覧・契約状態（Stripe の顧客ID 等）
                                 └─ tenants/<ID>.db   会社ごとのデータ（会社1社＝ファイル1つ）
```

- **会社ごとにDBファイルを分ける**構成です。他社のデータを読み書きする経路がなく、バックアップ・書き出し・削除が会社単位でできます。
- **単一サーバー前提**です（SQLite）。数百社・数千人規模までは1台で足りる想定ですが、冗長化（複数台）はできません。規模が出てきたら PostgreSQL への移行を検討してください（データ層は `src/server/repo.ts` と各ルートに集中しています）。

## 3. 起動

```bash
cp .env.example .env   # 値を埋める
docker compose up -d --build
curl https://<ドメイン>/api/health      # {"ok":true}
```

- 公開サイトは `https://<ドメイン>/`、アプリは `/app/` です。
- データは Docker のボリューム `app-data`（コンテナ内 `/data`）にあります。**ボリュームを消すとデータが消えます**。
- 更新: `git pull && docker compose up -d --build`。DB のスキーマ変更（マイグレーション）は、各社のDBを開くときに自動で適用されます。更新の前に必ずバックアップを取ってください。

> この Dockerfile / compose は、手元の環境では Docker を使えなかったため、**イメージのビルドは未検証**です（アプリ本体のビルドと、`node dist-server/index.js` での起動は確認済み）。初回は、ステージングでビルドと起動を確認してください。

## 4. Stripe の設定

**先にテストモードで全部通してから、本番キーに切り替えます。**

1. **商品と料金**を作る: 商品名（例: 勤怠管理）、**通貨 JPY、月次の定期課金、単価300円、数量課金（licensed / 数量はお客様の人数）**。料金の ID（`price_...`）を `STRIPE_PRICE_ID` に設定
2. **Webhook** を追加: URL `https://<ドメイン>/api/billing/webhook`。送信するイベントは次の6つだけにする
   - `checkout.session.completed`
   - `customer.subscription.created` / `customer.subscription.updated` / `customer.subscription.deleted`
   - `invoice.paid` / `invoice.payment_failed`

   表示される署名シークレット（`whsec_...`）を `STRIPE_WEBHOOK_SECRET` に設定
3. **カスタマーポータル**を有効にする（設定 → Billing → カスタマーポータル）: 「支払い方法の更新」「請求書履歴」「サブスクリプションのキャンセル」を許可。**ここを保存しないと「請求・お支払い方法の管理」が開けません**
4. **消費税**: Stripe Tax を使う場合は有効化し、`STRIPE_AUTOMATIC_TAX=1`。使わない場合は、料金を税込で設定するか、税率を料金に設定する
5. シークレットキー（`sk_live_...`）を `STRIPE_SECRET_KEY` に設定し、アプリを再起動
6. ローカルでの確認: `stripe listen --forward-to localhost:8787/api/billing/webhook` で表示される `whsec_` を使う

**動作の要点**
- 申し込みは Checkout、人数が増減したら数量を自動で更新（日割り）。更新に失敗しても社員の登録は止まらず、1時間ごとのジョブが再同期します
- 支払いに失敗すると `past_due`。**14日の猶予**のあと閲覧のみになります
- Webhook は署名を検証し、同じイベントの再配信・古いイベントの逆戻りは無視します
- ⚠️ **この実装は、Stripe 本体との実接続を一度も行っていません**（テストは、Stripe SDK の署名機能とダミーのゲートウェイで行いました）。テストモードで、申し込み → 人数変更 → 支払い失敗 → 解約 を必ず通してください。API の仕様変更に備え、`stripe` のバージョンは固定して更新時に確認します

## 5. バックアップと復元

```bash
docker compose exec app node --disable-warning=ExperimentalWarning dist-server/cli.js backup /data/backups --keep 14
# または deploy/backup.sh を cron で（毎日）
```

- SQLite の `VACUUM INTO` で、稼働中でも一貫したスナップショットを `backups/YYYYMMDD-HHMMSS/` に作ります（`control.db` と、会社ごとの `<ID>.db`）
- **同じサーバーのディスクにあるだけでは、サーバーの故障で一緒に失われます。** 別の場所への複製（`deploy/backup.sh` の末尾の例）を必ず設定してください
- **復元**: アプリを止め、`control.db` を `/data/control.db` に、`<ID>.db` を `/data/tenants/` に戻して、アプリを起動します。1社だけ戻す場合は、その会社の `<ID>.db` だけを置き換えます（`-wal` `-shm` ファイルは削除する）
- 復元の手順は、**公開前に一度、別環境で実際に試してください**

## 6. 解約・削除・データ提供

- 解約すると、会社は**閲覧のみ**になります（管理者は「会社設定」から全データをJSONで書き出せます）
- 規約では、契約終了から30日で削除する定めです（`src/brand.ts` の `policy.retentionDays`）。削除は手動です:
  ```bash
  ops list                                   # 会社の一覧（企業ID・状態・人数）
  ops export <企業ID> /data/export.json       # 念のため書き出し
  ops backup                                 # 念のためバックアップ
  ops delete <企業ID> --yes                  # 完全に削除（元に戻せません）
  ops reset-2fa <企業ID> <社員ID>             # 二段階認証の解除（管理者がスマートフォンも回復コードも失った場合。本人確認は運営者が行う）
  ```
  （`ops` は `docker compose exec app node --disable-warning=ExperimentalWarning dist-server/cli.js` の略）
- バックアップには削除済みの会社のデータが残るため、**バックアップの保持期間（既定14世代）も、プライバシーポリシーの保存期間に反映してください**
- 利用の停止（未払いなど）: `ops set-status <企業ID> suspended`。ログインできなくなります

### 性能の目安（実測）

1社1ファイルのSQLite＋1プロセスの構成での、社員数ごとの応答時間の目安です（開発用サンドボックスでの実測。本番の機材では、必ず同じ手順で測り直してください）。

- 測り方: `npx tsx scripts/perf.mts 300`（引数は社員数。メモリ上のDBに、半年分の打刻を作って、各APIの応答時間を測る。メモリも見るなら `node --expose-gc --import tsx scripts/perf.mts 1000`）
- 本人の打刻・今日の状態・本人の勤怠: 1人分だけ読み込むため、社員数にほぼ依存しない（1〜20ms）
- 管理者のダッシュボード・勤怠一覧（全社員を集計）:
  - **初回（プロセスの起動後・日付が変わった後・会社設定/祝日を変更した後）は、打刻の件数（社員数 × 約130日 × 4件）に比例して遅い**: 社員300人で 約1.1秒、社員1000人（打刻 約54万件）でダッシュボード 約5〜6秒、勤怠一覧 約6〜7秒（測るたびに±20%程度ばらつく）。この間は他の操作も待たされる（単一プロセス）
  - **その後は差分だけを反映する**: 打刻が入った・1分経った後の再表示は、社員1000人でも 20〜40ms（打刻50件が入った直後でも）。打刻の表は追記のみなので、前回より後の打刻だけを読み、影響のある社員の集計だけを捨てる
- 差分の反映の仕組み（`src/server/repo.ts` の `snapshot`）:
  - 社員・シフト・有給の変更は、トリガーが変更した社員を `data_changes` に記録する。**その社員の分だけ**読み直して、集計を差分で更新する（一度に2000件を超える変更、記録が欠けているときは作り直す。記録は定期ジョブで新しい2万件だけ残す）
  - 設定・祝日の変更は、`data_rev`（変更回数。トリガーが数える）で検知して、集計を作り直す。**別のプロセスが同じDBに書いた場合も、検知できる**
  - 日付が変わった・ロールバックがあった・読み込んだ範囲より前の日付の打刻が増えた（昔の記録の追加）ときも、作り直す
  - 本日の打刻は、月・期間・リスクの集計（前日まで）に入らないので、その日の予定・実績だけを捨てる。前日以前の打刻（修正申請の承認など）は、その社員の集計を捨てる
  - 時刻だけが進んだときは、前日から続く勤務（退勤なし）のある社員の集計だけを捨てる
  - 差分で更新した結果が、ゼロから作った結果と一致することは、`src/server/live.test.ts` が、打刻の追加・時刻の経過・各種の変更をランダムに繰り返して毎回照合している
- メモリ: 社員1000人・打刻54万件の集計を残しておくのに、約400MB（測定用の仕掛けを含む）。会社ごとに1つ残し、打刻の件数の合計が200万件を超えたら、使っていない会社のものから捨てる。大きな会社を多数同居させるときは、メモリを見て調整する（`LIVE_MAX_WEIGHT`）
- 1人分の集計と、前の協定期間の最終月（`backTo`）の集計は、同じDB・同じ変更回数・同じ分の間（最長2分）だけ使い回す。**別のプロセスが同じDBに書く運用では、これらは同じ分の間、古い集計になる**。勤務中の経過時間も、同じ分の間は更新されない（最大59秒の遅れ）
- 会社のDB接続が閉じられるとき（使われていない会社の整理・会社の削除）、その会社の集計は破棄される
- **先に作っておく**: 起動の1秒後に、DBファイルが10MB以上の会社（社員150人前後から）の集計を作り、その後20秒ごとに、残してある集計を最新にする（日付が変わった直後の作り直しも、これで済む）。会社ごとに、他のリクエストを処理する間をあける。ただし、1社の集計を作る間（社員1000人で約5秒）は、その1社の分だけ、他の操作も待たされる。メモリの上限に収まらない会社は、先には作らない
- 変更の種類ごとの再表示（社員1000人）: シフト1件・社員1人・有給1件の変更 約20〜40ms。**会社設定・祝日の変更は、作り直しで約5秒**
- 残る課題: 数千人規模では、過去の月の集計を保存すること、作り直しを複数のプロセスに分けることを検討する

## 8. セキュリティの現状と、未対応のこと

診断の結果と、対応状況の一覧は、[security-assessment.md](security-assessment.md) にまとめています。

実装済み:
- パスワード: scrypt（コスト N=2^15。パラメータはハッシュ文字列に入れ、ログイン成功時に古い形式を作り直す。非同期で、リクエスト処理を止めない）。一時パスワード（ランダム生成）は、大量登録で全社のログインを待たせないよう、軽いコストで保存し、初回ログインで作り直す。パスワード変更は成功も回数を数えて制限
- ログイン: 社員ID×IP単位（5回失敗で5分）・アカウント単位（20回失敗で15分。失敗の回数は、30分で忘れる）・IP単位の制限。**アカウント全体のロックは、前にログインに成功した端末（Cookie `kd`、180日）からは、パスワードの確認に進める**（他人が失敗を重ねて、本人を締め出せない）。端末の印は、パスワードの変更・再設定・退職で無効になる
- IPの判定: `TRUST_PROXY=1` のとき、X-Forwarded-For の**右端**（直前のプロキシが付けた値）を使う。**XFF を上書き（または右端に追記）するプロキシの背後でだけ有効にすること**。付属の Caddy 構成は問題ない。直接公開、または前段に別のプロキシ・CDN がある構成では、信頼するプロキシの設定（Caddy の `trusted_proxies` など）を確認する。プロキシの背後なのに `TRUST_PROXY` を付けないと、全員が同じIPに見え、少数の失敗で全員がログインできなくなる
- 本文サイズの上限（通常64KB／Stripe通知1MB／CSV取り込み1MB）。CSV取り込みは、解析の前に行数・列数を確認し、会社ごとに回数を制限（解析は同期処理で重いため）
- 会社ごとのDB分離、Cookie（HttpOnly・SameSite・本番はSecure）、CSRF対策（別オリジン・Origin不正・Sec-Fetch-Site: cross-site を拒否）、CSP（base-uri・form-action・object-src を含む）などのヘッダー
- **二段階認証（TOTP, RFC 6238）**: 認証アプリのコード（前後30秒のずれを許容、使用済みのコードは再利用不可・同時送信でも1回だけ）、回復コード8個（1回限り・ハッシュ保存）、5回失敗で5分ロック。**設定を始めるときは、パスワードの再入力が必要**（セッションを奪われても、第三者が登録して本人を締め出せない）。秘密鍵は `SECRET_KEY` で暗号化（AES-256-GCM）して保存。**本番（NODE_ENV=production）では、SECRET_KEY（32文字以上）が無いと起動しない**。会社の設定で管理者に必須にできる（未設定の管理者は、設定が済むまで他の操作が不可）。管理者・運用コマンドで解除できる
- パスワード再設定（1回限り・60分・Hostヘッダ非依存。**本人のパスワード変更・管理者の再発行・退職・メールアドレスの変更で、発行済みのリンクは無効になる**）、一時パスワードの強制変更、最後の管理者の保護、操作記録（監査ログ。存在しない社員IDは、操作者として記録しない）
- Stripe: 署名検証、重複配信・古いイベントの無視、**運営者が停止した会社はStripeの通知で自動復活しない**。座席数の同期は、会社ごとに直列（古い人数が最後に残らない）
- **登録時のメールアドレス確認**: 登録メールのリンク（24時間・1回限り・ハッシュで保存、再送すると古いリンクは無効、アドレス変更後は変更前宛のリンクも無効）。未確認の間は、**お申し込み（決済）・トライアル終了の案内メール・パスワード再設定メールが使えない**。トライアル自体は未確認でも使える。入力ミスは、ログイン後の画面上部から直して再送できる。送り先を変えて再送するメールの本文には、入力した氏名を入れない。APP_URL 未設定でメールを送れない環境では、確認済みとして登録される。この機能の導入前に登録済みの会社は、確認済みとして引き継ぐ
- 案内メールに入る「会社名・お名前・部署・役職」は、改行・URL・短縮URL・ドメイン名・全角のURLを受け付けない（登録時と、登録後の変更・CSV取り込みの両方）。社員のメールアドレスは、在籍中の社員のあいだで重複できない（パスワード再設定の案内が、複数の社員に届かないように）
- CSV出力は、数式として実行されうる文字列（`= + - @` で始まる）を無害化
- 本番でSMTP未設定のとき、メール本文（再設定リンク）をログに出さない
- データ・バックアップのファイルとディレクトリは、実行ユーザーだけが読める（0600 / 0700）。コンテナは、`no-new-privileges`・全権限の放棄（cap_drop: ALL）、アプリのコードは書き込み不可

**この節の確認について**: 実装とは別の担当による、コードのレビューと、ローカルの環境に対する攻撃の試行（認証、認可とテナント分離、注入・依存関係・配備設定の3つの観点）を行い、再現できた指摘を修正しました（結果は docs/security-assessment.md）。ただし、これは**書いた本人の側で手配した自己点検で、第三者による脆弱性診断の代わりにはなりません**。公開前に、外部の専門家による診断（侵入テスト）を受けることを推奨します。

**未対応・運用上の注意**:
- 登録時の確認メールそのものは、他人のアドレスにも届きます。対策として、IPごとに1時間10回、**同じアドレス宛は24時間に3回（登録・再送・送り先の変更で共通）、サービス全体で1時間300回**、パスワード再設定は**同じ宛先へ全社で1時間6回**までに制限しています。副作用として、第三者が他人のアドレスで3回登録を試みると、その本人の登録が24時間できなくなり、全体の枠を使い切られると、新規登録が止まります（運営に連絡があれば、サービスの再起動で解除できます）。複数のIPを使った攻撃で、別々のアドレスに少しずつ送る分は防げません（Gmail の `+` や `.` による別名も同じアドレスとは数えません）。送信元ドメインの SPF・DKIM・DMARC と、必要なら CAPTCHA（Cloudflare Turnstile 等）の導入を検討してください。制限はメモリ保持で、再起動で消えます
- メール未確認のまま放置された会社は、自動では削除・停止されません（無料トライアルで会社を大量に作られると、DBファイルとファイルディスクリプタが増えます。コンテナのファイルディスクリプタの上限（LimitNOFILE）を、十分に大きくしてください。Docker の既定では問題になりません）
- **アカウント全体のロック中は、前に成功した端末のない利用者（新しい端末、Cookie を消した端末）は、最長15分ログインできません**。他人が15分ごとに20回失敗させると、これを続けられます。管理者が締め出された場合は、`ops` で状況を確認し、IPやアクセスログを確認してください
- 管理者は、他の管理者のパスワードと二段階認証を、第二要素なしで、再発行・解除できます（設計）。管理者のセッションを奪われると、他の管理者も乗っ取られます。管理者の人数を絞り、二段階認証を必須にしてください。また、管理者が2人いると、片方を一時的に一般社員に降格して、自分の修正申請を承認できます（操作記録に残ります）
- 共用端末の暗証番号は6桁で、端末のトークンを持つ内部者は、時間をかければ当てられます（社員ごとに5回失敗で5分ロック。他人名義の打刻に使われる可能性）。DBが流出すると、暗証番号・カード番号のハッシュは、短いため、割り出されます。暗証番号とカードは、ソルト付きのハッシュ（暗証番号はscrypt、カードは会社ごとのSHA-256）です
- 打刻端末のURL（`#/kiosk?t=…`）を開くと、その端末のトークンが入れ替わります。端末を物理的に操作できる人だけが、悪用できます
- 認証済みの利用者が、成功するログインを繰り返すことは、制限していません（自社のDBが増えるだけ）
- パスワードの強度の検査は、長さ（登録10文字・その他8文字）だけです
- SSO
- 操作記録は、画面・CSVから閲覧できる（管理者のみ）が、データベース上では削除・変更を禁止していない（改ざん防止の仕組みは無い）。保管期間の上限もない。長期保管や外部への転送が必要なら、定期的にCSVを保存する
- ログイン失敗などの試行回数がメモリ保持（再起動で消える）。複数台構成では共有されない
- パスワードの計算はNodeのスレッドプール（既定4本）で行うため、大量の同時ログイン試行があると、他のログインが遅くなります（IP単位の制限で緩和）
- 会社の管理者がいなくなった場合の復旧手順（現状は運用者が `ops` とDB操作で対応）

## 9. 労働時間の計算の前提と簡略化

社労士・弁護士への確認依頼には、[docs/labor-rules-review.md](labor-rules-review.md)（ルール一覧・計算例・確認してほしい点）をお使いください。

集計・警告は参考情報です。**公開前に、社会保険労務士に、次の前提が貴社の就業規則・労使協定に合うかを確認してもらってください。**

### 判定のしかた（根拠）

| 区分 | 判定 | 根拠 |
|---|---|---|
| 通常 | 日8時間超、週40時間超（日の時間外を除く） | 労基法32条 |
| 1か月単位・1年単位・1週間単位の変形 | ①日: 所定が8時間超の日はその所定を超えた分、それ以外は8時間超 → ②週: 所定が40時間超の週はその所定を超えた分、それ以外は40時間超（日の分を除く） → ③期間: 法定労働時間の総枠（40×期間の日数÷7）超（日・週の分を除く）。重複しない | [厚生労働省 静岡労働局の資料](https://jsite.mhlw.go.jp/shizuoka-roudoukyoku/var/rev0/0123/3919/2017111615407.pdf)、[1年単位の変形労働時間制（厚生労働省）](https://www.mhlw.go.jp/shinsai_jouhou/faq_03.html) |

### 簡略化していること（実運用で合わない場合は個別に確認が必要）

- 変形期間の途中から始まる週・途中で終わる週（月をまたぐ週など）は、週の判定をせず、期間の総枠で判定します。
- 時間外は「発生した日」（累計がしきい値を超えた日）に割り当てます。月をまたぐ週の週超過は、超えた日の月に入ります。
- **1年単位の変形の要件（労働日数の上限280日、1日10時間・週52時間の上限、連続労働日数、対象期間の労使協定の届出）は、チェックしていません。**シフトの作成・届出は運用側で確認してください。
- 1年単位の変形期間の途中で入社・退職した社員の賃金精算（途中退職時の清算）は扱いません。
- フレックスタイム制の「清算期間中の不足時間の繰越」「コアタイム・フレキシブルタイムの違反判定」は、注記・表示のみで、集計には影響しません。
- 交替制（8時間3交替など）で、番方による休日（継続24時間）を休日とする特例は扱いません。休日は暦日で判定します。
- 週の法定労働時間が44時間（特例措置対象事業場）の設定は、日の8時間を変えず、週・総枠の判定だけに使います。通常の勤務・1か月単位の変形・清算期間1か月以内のフレックスに適用し、1年単位・1週間単位の変形と、清算期間が1か月を超えるフレックスは40時間のままです（労基則25条の2。[条文](https://www.mhlw.go.jp/web/t_doc?dataId=73023000&dataType=0&pageNo=1)）。
- 締め日・協定期間の起算月・清算期間・週44時間などの設定を変えると、**過去の月の集計も、新しい設定で再計算されます**（設定の履歴は持っていません）。給与を確定した月の数字が変わる可能性があるので、変更は期の切り替わりに行い、確定済みの月はCSVで保存してください。
- 日別の「時間外」は、通常の勤務でも、日8時間超と週40時間超を合わせた、その日に発生した時間外です。週が月・締め日をまたぐ場合は、月の前後の週も含めて判定し、超えた日の月に付きます。
- 勤怠一覧・給与用CSVで選べる月は、今の協定期間の月と、その直前の月（前の協定期間の最終月）です。それより前の月は、システムからは出力できません（過去の月は、毎月のCSV保存か、全データの書き出しをご利用ください）。
- 退勤が無いまま12時間を超えて続く勤務は、打刻漏れとして、新しい出勤を受け付けます（前の勤務は「退勤打刻なし」として残り、修正申請の対象になります）。12時間以内は日またぎの勤務とみなし、出勤を拒否します。
- 変形・フレックスの社員の「本日の集計」（打刻画面）は、日8時間のしきい値による目安です。
- 月末見込は、これまでの実績が所定の何倍だったかのペースを、残りの予定に当てはめた推計です。
- 位置情報の判定は、ブラウザから送られた値を使うため、端末側で書き換えられる可能性があります（不正の完全な防止ではなく、確認の目安です）。

### 打刻手段の運用メモ

- **共用の打刻端末**: 会社設定で端末を登録し、表示されるURLを端末のブラウザで開く（トークンは端末に保存され、URLからは消えます。失くした場合は端末を無効にして登録し直す）。社員は ICカード（キーボードとして動作する USB カードリーダーが、カード番号＋Enter を入力する方式）か、社員ID＋6桁の暗証番号で確認する。確認は90秒・1回限り。暗証番号は、同じ社員に5回続けて失敗すると5分ロックされる。**カードリーダー実機での動作は検証していません**（キー入力の再現でのみ確認）。
- **位置情報**: 会社設定で「記録する」「範囲外では出勤できない」を選べる（退勤・休憩は止めず、範囲外として記録・表示する）。位置情報は個人情報なので、社員への周知とプライバシーポリシーへの記載が必要（ひな形に追記済み・要確認）。無効のときは、送られてきても保存しない。
- **給与用CSV**: 勤怠一覧の「給与用CSV」から、社員ごとの月次集計・日別明細を出力（UTF-8・BOMつき）。給与ソフトごとの取り込み形式には合わせていません。
